# Private proposal: actual word-table logical extents

No live tools, registry, source header, target, lock or layout was changed. `logical_extent_proposal.py` is a reviewable acceptance model, not an alternate build/scorer. `test_logical_extent_proposal.py` passes33meaningful cases with captured exit0. `proposal_validation.json` applies it to this real independently linked native module: all89table relocations remain inside356retained bytes, both true initializer blocks remain32bytes, and the complete original assets/us/data.bin hash is unchanged.

C82's original table starts at8002D558, four-byte aligned but eight modulo16. It has89actualentries/356bytes. IDO's input .rodata is368bytes because of12trailing alignment-zero bytes. The following original12-byte interval has8nonzero bytes; its SHA is in full_module_proofs.json. Linking or claiming the entire padded section at this address would overwrite real neighboring data. The proposed logical output must retain every actual table byte and every table relocation, exclude only these proved alignment zeros, and preserve the following original bytes. This is an input-section ownership rule, never a scoring mask or target change.

A supported implementation should keep the current default16-byte owner alignment, adding explicit reviewed `alignment:4` plus an exact logical extent and expected emitted alignment extent for this genuine word table. Validate positive integer sizes, address/size alignment, natural round-up, zero excluded tail, no relocation or retained symbol in that tail, original slot hash, no overlap and complete protected container identity. Reject any nonzero excluded byte, malformed geometry, overlapping row, changed slot or changed neighbor. Generated linker/output helpers must emit exactly356bytes at8002D558 with real four-byte alignment and retain all neighboring bytes; they must not hand-edit protected assembly or widen the owned slot over unrelated data. Registry assertions must continue to check actual linked start/length.

The private model covers only validated logical-section content and exact container composition. It intentionally does not patch an ELF, modify an object, weaken canonical target scoring, register source storage, migrate a lock or pretend the complete ROM has been rebuilt. Root must route through existing reviewed ownership/promotion tools and demonstrate the unchanged whole-ROM gate. The two literal initializer templates emit a genuine32-byte .data section at8002D4D0; that separately proved section also needs actual ownership or a grounded extern-data source representation. Current registry expects one owner per input section and one row per function, so a single function owning two real sections requires an explicit reviewed representation rather than a fabricated owner name.
